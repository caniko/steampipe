## 2 — Unwrap Audit

Audit every use of `.unwrap()` and `.expect()` in non-test code:
1. For each occurrence, determine if the unwrap can actually panic at runtime
2. Replace panicking unwraps with proper error handling:
   - Use `?` with the crate's error type where possible
   - Use `ok_or_else(|| ...)` or `map_err(|e| ...)` for context
   - Use `if let` or `match` when the None/Err case needs specific handling
3. Keep `.expect("reason")` only where the invariant is truly guaranteed and document why
4. Leave `.unwrap()` in test code (#[cfg(test)]) alone — it's fine there

Do not change logic or control flow beyond replacing the error handling.
Commit with a summary of how many unwraps were replaced.

5. Do not add validation that duplicates the type system

# Stage: Design

## 1 — Code Reorganization

Reorganize the project's file and module structure for readability:

Phase 1 — Measure: list every `.rs` file with its line count. Identify files >300 lines (split candidates) and files <30 lines (merge candidates).

Phase 2 — Split large files: for each file >300 lines, extract cohesive blocks into focused submodules. Target 80–300 lines per file. Create `mod.rs` re-exporting the public API.

Phase 3 — Merge tiny files: for each file <30 lines that is NOT a module entry point, merge its contents into the parent module or a sibling file.

Phase 4 — Deduplicate: extract shared logic into reusable functions or traits. Merge near-identical helpers that differ only in a parameter.

Phase 5 — Organize: ensure the module tree mirrors the domain hierarchy. Flatten nesting beyond 3 levels. Every `mod.rs` must have `//!` docs. Add `pub use` barrel exports at crate root.

Phase 6 — Verify: update all `use`, `mod`, re-export paths. Run `cargo check` after every structural change. Run `cargo test` at the end. No circular dependencies.

Do not alter business logic. Each commit should be a single atomic reorganization step.

## 2 — Type Safety

Review the codebase and apply zero-cost abstractions:
1. Wrap domain-specific primitives in newtypes (IDs, paths, keys)
2. Refactor runtime state flags into compile-time typestates where builder patterns exist
3. Replace String parameters that represent a fixed set with enums
4. Replace unnecessary owned types with references or `Cow<'_, str>`
5. Swap `Vec` for `SmallVec` or fixed arrays for predictably small collections (≤8 elements)
6. Convert `Box<dyn Trait>` to `impl Trait` where concrete type is known
7. Replace multiple bool parameters with descriptive enums
8. Do not refactor types on serialization boundaries

## 3 — Trait Design

Analyze for missing trait abstractions:
1. Find structs with same logical behavior but no shared trait
2. Identify methods accepting concrete types but using only a subset of the API
3. Look for match/if-else chains dispatching on type tags
4. For each concept, define a minimal trait (1–5 methods, named after capability)
5. Update function signatures to accept `impl Trait` or `&dyn Trait`
6. Audit existing traits: split fat traits (>5 methods), extract optional extensions
7. Do not create traits with a single implementor unless it's a documented extension point

Run `cargo check` after each extraction. Commit each trait separately.
